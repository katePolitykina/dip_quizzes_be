# Software Development and Implementation Report

## 1. Introduction

This document presents the technical documentation for the software development and implementation stage of the project contained in the repository `/home/user/projects/dip`. The system is not a single executable artifact but a coordinated full-stack application composed of a backend module named `dip2` and a frontend module named `dip_quizzes`. Taken together, these modules implement an interactive quiz platform that supports account registration, guest access, quiz authoring, room creation, team configuration, real-time game orchestration, confidence-based scoring, and generation of final game reports. The codebase therefore represents more than a traditional data-entry system. It combines persistent business data, transient session state, security, timed interaction, and bidirectional network communication within one coherent technical solution.

From the perspective of software engineering, the application addresses two fundamentally different classes of problem. The first class concerns durable data and classic business workflows. This includes user accounts, user profile maintenance, quiz creation, quiz update operations, and access control around authored content. These capabilities require transactional persistence, validation, and clear ownership rules. The second class concerns volatile, rapidly changing runtime state. This includes room membership, live question progression, team role assignment, answer confirmation, pause and resume behavior, and leaderboard updates delivered to multiple participants at once. These features require predictable concurrency control, low-latency communication, and infrastructure capable of propagating state changes immediately. The implemented design responds to this dual character by separating persistent quiz content from volatile game-session state while still exposing both through one integrated platform.

The repository structure reflects this separation very clearly. The backend module `dip2` is implemented in Java using Spring Boot and provides REST APIs, WebSocket endpoints, business services, persistence, authentication, authorization, and room-state orchestration. The frontend module `dip_quizzes` is implemented in TypeScript with React and serves as a single-page application through which users authenticate, manage quizzes, enter game rooms, and participate in live sessions. Rather than treating the frontend as a passive template layer, the implementation gives it a meaningful responsibility for routing, interaction flow, state synchronization, and real-time event handling. At the same time, the backend retains control over all authoritative business decisions, which is a sound engineering choice for consistency and security.

This report is written directly from the implemented code, not from a speculative design description. The analysis is therefore grounded in the actual classes, modules, configuration files, tests, and build definitions present in the repository. Where the implementation suggests implicit design decisions, those decisions are reconstructed and explained in engineering terms. The purpose of the document is not only to describe what technologies were used, but to justify why they were used, how the software is architected, how the principal classes interact, how the key modules were debugged and verified, and how a developer can assemble and run the solution.

## 2. Technology Stack Justification

The technology stack selected for this project is appropriate for the scale, complexity, and interaction model of the implemented system. The backend is based on Java 17 and Spring Boot 3.3.5, while the frontend is based on TypeScript, React 19, Redux Toolkit, and Vite. In addition, the backend integrates PostgreSQL for durable relational persistence and Redis for volatile room-state storage. The system also uses JWT-based authentication, Google OAuth2 login, and WebSocket/STOMP messaging for real-time updates.

The choice of **Java 17** for the backend is well justified. The backend is responsible for non-trivial domain modeling, access control, request validation, persistence coordination, live session orchestration, and timed event processing. These are all areas in which Java remains especially strong. The language offers explicit typing, strong tooling support, mature libraries, and predictable structure for systems whose complexity arises from domain rules rather than algorithmic novelty alone. The codebase makes heavy use of classes such as `AuthService`, `QuizService`, `RoomService`, `GameLoopService`, `JwtService`, and structured DTO records, and Java’s object-oriented model fits this implementation style naturally. Java 17 is also a long-term support version, which is advantageous in a project expected to be maintainable and stable over time. The configuration additionally enables virtual-thread support in Spring, indicating alignment with contemporary JVM execution models.

The use of **Spring Boot 3.3.5** is technically sound because the backend must combine several infrastructure concerns in one application: HTTP APIs, authentication, OAuth2 login, relational persistence, Redis integration, validation, and WebSocket messaging. Spring Boot dramatically reduces boilerplate in these areas without removing architectural clarity. In the present project, REST controllers remain small and declarative, while services encapsulate domain logic. This is a strong sign that the framework is being used appropriately rather than as an accidental source of complexity. Spring Boot also contributes production-ready configuration conventions, testing support, and a coherent dependency ecosystem, which is especially valuable in academic or professional engineering work where traceability and maintainability matter.

The adoption of **Spring Security** is not incidental. The system distinguishes among locally registered users, OAuth-authenticated users, and guests, and then applies different privileges depending on role and endpoint. For example, a registered user may manage quizzes and create rooms, whereas a guest may join a room and participate in a session but may not access profile or quiz-management functionality. The implemented `SecurityConfig` class encodes these constraints directly and clearly. This is precisely the kind of security boundary management for which Spring Security is suited. The presence of both HTTP and WebSocket authentication further strengthens the case for a mature security framework rather than a custom solution.

The choice of **Spring Data JPA** with **PostgreSQL** is justified by the nature of the durable business data. User accounts, quizzes, questions, and answers are all inherently relational entities. A user authors many quizzes, a quiz owns many questions, and a question owns many answers. The JPA entity classes `User`, `Quiz`, `Question`, and `Answer` map this structure directly. The use of JPA allows the developer to work at the level of aggregates and relationships rather than hand-writing repetitive SQL-based object mapping. PostgreSQL is a suitable database engine because it is transactional, mature, widely deployed, and reliable for the kind of structured content stored here. The code indicates that quiz authoring data is expected to be durable and queryable, which aligns with relational persistence rather than document-oriented or key-value storage.

The use of **Redis** for room-state storage is equally well reasoned, but for different reasons. Live game sessions are transient and mutable. They contain participant assignments, teams, question progression state, answer selections, leaderboard data, timestamps, and final reports. This information changes often and is more naturally treated as runtime session state than as normalized relational data. The code formalizes this through the `GameSessionStore` abstraction, with support for Redis-backed and in-memory implementations. This is a good design because it decouples the room state model from one storage engine while still acknowledging that volatile live-session data is better handled separately from authored content. Redis is therefore used not as a general-purpose database replacement, but as a specialized runtime-state mechanism.

The backend also uses **Spring WebSocket** with **STOMP-style messaging**, which is essential for the application’s real-time interaction requirements. A quiz room is inherently multi-user and event-driven. The host must be able to start a game, pause it, advance it, or remove a participant. Participants must receive immediate updates when a question starts, when a team answer is confirmed, when the histogram of confirmed answers changes, or when a final report is produced. Polling the backend through REST endpoints would be inefficient and would produce a poor user experience. WebSocket communication is therefore the correct technical choice. The implemented `RoomMessageController`, `JwtStompChannelInterceptor`, and `RoomRealtimeService` together show a deliberate messaging architecture rather than an improvised socket integration.

On the frontend, the use of **TypeScript** is strongly justified by the number of data contracts exchanged with the backend. The client consumes authentication payloads, quiz details, room snapshots, scoreboards, team events, and final reports. It also emits strongly structured requests for login, room creation, team updates, and WebSocket commands. TypeScript is valuable here because it makes these contracts explicit and verifiable at compile time. In a real-time client, unchecked dynamic objects often become a major source of defects; the current implementation avoids much of that risk by using static typing across the UI and API layers.

The use of **React 19** is appropriate because the frontend is a stateful single-page application with multiple screens and interaction modes: authentication views, a dashboard, a quiz editor, a join-room screen, a lobby, a game session interface, and a detailed result screen. React is particularly effective for managing view composition, derived state, and conditional rendering in such environments. The main `App` component acts as a coordinator for route state, authentication bootstrap, quiz loading, room re-entry, and WebSocket lifecycle management, while smaller components focus on specific parts of the interface. This separation is a good fit for React’s component architecture.

The selection of **Redux Toolkit** reflects the fact that not all frontend state is local to one component. Authentication state, quiz library data, and room session state are cross-cutting concerns that affect multiple views at once. Redux Toolkit provides a disciplined structure for asynchronous actions and global state mutation. In this project, `authSlice`, `quizzesSlice`, and `roomSlice` manage logically distinct parts of the application while keeping their transitions explicit. At the same time, the developer correctly avoids using Redux for everything. The quiz editor uses its own `QuizContext` and reducer because editing state is local to that workflow and benefits from a lighter, screen-local model. This mixed strategy is an example of appropriate rather than excessive state management.

The choice of **Vite** as the frontend build tool is also appropriate. Vite offers fast development startup, straightforward TypeScript integration, and modern bundling behavior for React applications. The repository’s `package.json` and build scripts show a minimal but effective development pipeline built around `vite`, `tsc -b`, and ESLint. This is a practical choice for a frontend that benefits from fast iteration but does not require a heavy framework-specific build system.

Although the repository does not explicitly prescribe one development environment, the most suitable **IDE** for this solution is IntelliJ IDEA with support for Java, Spring, Maven, TypeScript, and React. The project spans backend framework wiring, JPA entities, test execution, Docker-oriented setup, and frontend SPA development. A unified environment that can navigate from controller to service to repository, and from TypeScript component to reducer to API client, materially improves engineering productivity and reduces context-switching overhead. For this reason, IntelliJ IDEA is the most defensible IDE choice for the implemented stack.

## 3. Software Architecture and Interfaces

The software architecture is best described as a **layered full-stack client-server system**. It is not a microservice architecture, because the backend is deployed as one application and encapsulates multiple responsibilities internally. At the same time, it is not a monolithic UI served from backend templates. The frontend is an autonomous single-page application that communicates with the backend through HTTP and WebSocket interfaces. The result is a modular architecture in which the backend and frontend are separated by clearly defined contracts while remaining tightly coordinated around one domain.

### 3.1 Backend Architecture

Within the backend, the principal architectural pattern is a **layered service-oriented structure**. The outermost layer is the presentation layer, represented by REST controllers and the WebSocket message controller. These classes are intentionally thin. `AuthController`, `UserController`, `QuizController`, and `RoomController` receive validated requests and delegate immediately to service classes. `RoomMessageController` plays a similar role for incoming STOMP messages. This is a positive design trait because it prevents the accidental spread of business rules into transport-specific code and keeps the HTTP and WebSocket endpoints readable.

The core business logic resides in the **service layer**. `AuthService` handles user registration, credential validation, and guest token issuing. `UserService` handles user lookup and profile update logic. `QuizService` enforces quiz ownership, validates question structure, maps DTOs to entities, and produces response DTOs. `RoomService` manages room creation, membership, team assignment, role assignment, and room-level moderation actions. `GameLoopService` performs the most complex orchestration, including starting games, initializing runtime questions from persisted quiz content, tracking answers, scheduling question finalization, computing scores, recalculating leaderboards, and generating final reports. `RoomRealtimeService` is narrower in responsibility: it acts as a broadcast façade over the messaging layer so that other services do not need to know topic-formatting details. This distribution of responsibilities is coherent and keeps each class aligned with one domain concern.

Beneath the service layer, the project has two data-access strategies rather than one. Durable authored content is stored using the **persistence layer** built on Spring Data JPA repositories. `UserRepository` and `QuizRepository` are used by the business services responsible for persistent entities. In contrast, volatile room state is managed by the `GameSessionStore` abstraction, which can be backed by Redis or an in-memory implementation. This is a particularly important architectural decision. If room state had been forced into the same persistence approach as quizzes and users, the design would have been more cumbersome and less responsive. By separating persistent authoring data from transient gameplay data, the system reflects the actual lifecycle of the information it manages.

The backend also contains a distinct **security and infrastructure layer**. `SecurityConfig` defines endpoint authorization rules, integrates JWT filtering, and configures OAuth2 login. `JwtAuthenticationFilter` authenticates HTTP requests using bearer tokens. `JwtService` creates and parses tokens for both regular users and guests. `WebSocketConfig` enables STOMP messaging and configures the `/ws` endpoint. `JwtStompChannelInterceptor` authenticates incoming WebSocket connections and subscriptions, while `WebSocketSessionRegistry` supports session tracking and forced disconnection behavior. These classes are infrastructural rather than domain-specific, but they are crucial because the application’s correctness depends not only on business logic but also on who is allowed to execute which interactions.

From the standpoint of internal backend communication, the dominant pattern is **controller to service to repository/store**, with DTOs at the boundary and domain/state objects in the middle. A quiz creation request, for example, travels from `QuizController.createQuiz(...)` to `QuizService.createQuiz(...)`, where the request is validated, mapped to a `Quiz` aggregate, and persisted through `QuizRepository`. A room start request travels from `RoomMessageController.startGame(...)` to `GameLoopService.startGame(...)`, which retrieves the relevant quiz through `QuizRepository`, converts persisted `Question` and `Answer` entities into runtime `QuestionState` and `QuestionAnswerState` objects, stores the updated `GameSession` through `RoomService` and `GameSessionStore`, and broadcasts new state through `RoomRealtimeService`. The communication path is direct, structured, and consistent with the layered architecture.

### 3.2 Backend Interfaces

The backend exposes two principal categories of interface: **synchronous REST interfaces** and **asynchronous WebSocket/STOMP interfaces**. REST endpoints are used where request-response semantics are natural and sufficient. This includes authentication, profile retrieval and modification, quiz CRUD operations, room creation, room join and leave operations, and team-distribution management. These interfaces are represented by the controller methods in `AuthController`, `UserController`, `QuizController`, and `RoomController`.

The WebSocket/STOMP interface is used where low latency and server-initiated updates are necessary. Incoming commands are routed through application destinations such as `/app/rooms/{pin}/moderation`, `/app/rooms/{pin}/game/start`, `/app/rooms/{pin}/teams/{teamId}/selection`, `/app/rooms/{pin}/teams/{teamId}/confirm`, and `/app/rooms/{pin}/teams/{teamId}/sort-answers`. Outgoing state propagation is emitted to topic destinations such as `/topic/rooms/{pin}`, `/topic/rooms/{pin}/leaderboard`, and `/topic/rooms/{pin}/teams/{teamId}`. This distinction between command channels and event channels is an important part of the design, because it ensures that the backend remains the single authoritative owner of room state while clients remain consumers and initiators rather than direct mutators of shared data.

### 3.3 Frontend Architecture

The frontend follows a parallel but client-specific structure. At the top is the **view layer**, composed of React components representing application screens and reusable UI elements. The `App` component coordinates global application flow, while components such as `Dashboard`, `QuizEditorLayout`, `JoinView`, `ActiveLobby`, `GameSessionScreen`, and `DetailedResultScreen` render specific states of the user journey. This creates a presentation structure in which screen logic remains visible and relatively easy to reason about.

Underneath the view layer is the **state management layer**, which combines Redux Toolkit slices with a local context-based reducer for the quiz editor. This division is technically appropriate. Authentication state, room state, and the quiz catalog are global concerns and are therefore handled by `authSlice`, `quizzesSlice`, and `roomSlice`. The quiz editor, by contrast, is modeled through `QuizContext`, because its state is rich, interactive, and largely confined to one workflow. This avoids both unnecessary prop drilling and unnecessary globalization of view-local state.

The frontend also contains a **communication layer**. HTTP communication is encapsulated in `apiClient`, which centralizes request construction, token injection, error normalization, and endpoint definitions. Real-time communication is encapsulated in `RoomSocketClient`, which performs STOMP frame construction, authenticated connection establishment, reconnection handling, and event parsing. Around these modules is a small support layer of adapters and utilities such as `quizMapper`, `authStorage`, and `appConfig`, which translate between backend DTOs, local UI models, and runtime configuration.

Architecturally, the frontend behaves as a state-driven SPA rather than as a simple rendering client. It is responsible for navigation decisions, session restoration, conditional room bootstrapping from the current URL, socket lifecycle control, and orchestration of screen transitions such as dashboard to editor, editor to room, or room to detailed result. The backend remains authoritative for business state, but the frontend performs a substantial amount of workflow coordination, which is appropriate for an interactive real-time application.

### 3.4 Frontend Interfaces

The frontend consumes the backend through two mirrored interface families: typed REST calls and typed real-time message handling. The REST side is represented by the `apiClient` methods such as `login`, `register`, `guest`, `getMe`, `listQuizzes`, `getQuiz`, `createQuiz`, `updateQuiz`, `createRoom`, `joinRoom`, `leaveRoom`, `autoDistribute`, `updateTeams`, and `updateRoles`. Each method corresponds directly to a backend endpoint and returns typed objects that are subsequently stored in Redux or mapped into editor state.

The real-time interface is handled by `RoomSocketClient`, which connects to the backend WebSocket endpoint, authenticates using the stored JWT bearer token, subscribes to room and team topics, and converts incoming broker messages into application-level events. These events are then processed by the top-level application logic and Redux reducers. For example, room snapshots update `roomSlice`, histogram events update answer-count state, leaderboard events replace the room leaderboard projection, and team-selection events update the local representation of answer-confirmation progress.

This arrangement means that the frontend does not talk to the backend in an ad hoc manner from arbitrary components. Instead, communication is mediated through stable modules with explicit responsibilities. That improves maintainability, reduces duplication, and makes the codebase easier to explain in architectural terms.

## 5. Implementation Details

The implementation of the system is notable for how deliberately it separates concerns while still keeping the overall control flow understandable. The authentication workflow is a good example. `AuthController` merely exposes the endpoints `/api/auth/register`, `/api/auth/login`, and `/api/auth/guest`. The real logic lives in `AuthService`, which normalizes user input, checks for duplicate email addresses, uses the configured password encoder to hash credentials, persists new users, and issues JWT tokens through `JwtService`. The guest-authentication path follows the same overall pattern but bypasses durable user creation and instead generates a temporary identity embedded into the token payload. This is a pragmatic implementation decision because it allows guests to use the same authorization and WebSocket infrastructure as registered users without introducing a second identity model throughout the rest of the system.

The quiz-authoring workflow is similarly disciplined. `QuizService` does not merely save incoming JSON payloads. Before persisting a quiz, it validates that each question contains between two and four answers and that at least one answer is marked as correct. This is an important example of server-side business validation: even if the frontend attempted to enforce the same rule, the backend remains the authority. Once validated, the incoming request is mapped into the entity hierarchy `Quiz -> Question -> Answer`. The methods `replaceQuestions(...)` and `replaceAnswers(...)` are especially worth noting because they treat the quiz and question objects as aggregates that own their child collections. This simplifies update semantics and avoids fragmented collection mutation logic.

The room and game subsystems contain the most sophisticated implementation logic in the repository. `RoomService` creates room sessions, allocates unique PIN values using a constrained alphabet, enforces lobby-state restrictions, prevents duplicate nicknames in a room, manages participant join and leave operations, distributes players into teams, and assigns or updates team roles. These operations are wrapped by the `executeLocked(...)` mechanism provided by the session store abstraction. This is an important engineering feature. In a real-time environment, concurrent access to session state is unavoidable. Without explicit locking or atomic update control, operations such as multiple simultaneous joins, role updates, or answer submissions could corrupt room state. The implementation addresses this by centralizing mutable room operations behind a lock-aware store API.

`GameLoopService` then takes over once a game begins. When the host starts a game, the service verifies that the chosen quiz belongs to the initiating user, loads the persisted quiz, converts each stored question into a runtime `QuestionState`, verifies that the room is structurally ready for play, applies confidence-based marking overrides where provided, resets game progress, and starts the first question. From that point onward, the class becomes a state machine coordinator. It receives team answer selections, enforces that only captains may confirm answers, optionally applies confidence levels, records per-player answer details, tracks timestamps for response-time analysis, broadcasts selection and histogram events, schedules question finalization using a `ScheduledExecutorService`, computes scores when a question ends, and either advances to the next question or finalizes the game with a leaderboard and final report. The logic is state-driven and time-aware, which is exactly what such a subsystem requires.

The score computation mechanism itself is compact but conceptually sound. `ScoringUtility` receives a base weight, a correctness flag, a speed factor, a confidence level, and the applicable confidence-based marking settings. It then calculates the score multiplier based on whether the answer was correct and how confident the team declared itself to be. Correct answers may be rewarded more heavily at high confidence, while incorrect answers may incur a stronger penalty if the confidence declaration was unjustified. The speed factor further adjusts the score for correct answers. This design cleanly separates the mathematical scoring model from the orchestration code that gathers the inputs to it.

The real-time broadcasting path is also well implemented. Business services do not construct STOMP topics manually in every location. Instead, `RoomRealtimeService` provides methods such as `broadcastRoomState(...)`, `broadcastRoomEvent(...)`, `broadcastTeamSelection(...)`, `broadcastLeaderboard(...)`, and `broadcastTeamEvent(...)`. This isolates the message-broker details from the domain logic and makes the services easier to read. On the client side, `RoomSocketClient` performs the complementary role. It opens the WebSocket connection, sends a STOMP `CONNECT` frame with the bearer token, subscribes to room and team topics, parses incoming frames, reconnects with exponential backoff on interruption, and forwards message payloads to the application layer.

The frontend’s main `App` component shows a pragmatic integration strategy. Instead of depending on a large routing framework, it maintains route state using the browser history API and explicit path parsing functions. It then coordinates authentication bootstrap, profile fetching, quiz loading, room re-entry by URL, and socket lifecycle based on the current screen and authenticated state. This is not the only possible approach, but it is internally consistent and avoids unnecessary framework complexity. The Redux slices then manage the application-wide data domains. `authSlice` persists the session and profile state, `quizzesSlice` manages the quiz library and the active quiz, and `roomSlice` stores the live session snapshot, connection status, histogram data, hidden answers, leaderboard updates, and kick state. The quiz editor, by contrast, uses `QuizContext` and a reducer because that interaction pattern is more local and benefits from reducer semantics without needing global Redux exposure.

## 6. Testing, Debugging, and Integration Verification

The test suite in the backend module indicates that the project has been verified primarily through integration-style testing. This is an appropriate choice. The most important risks in this application arise not from isolated arithmetic or trivial helper logic, but from the interaction among validation, persistence, security, room state, and timed transitions. For this reason, tests such as `AuthFlowIntegrationTest`, `QuizManagementIntegrationTest`, `RoomManagementIntegrationTest`, and `GameEngineIntegrationTest` provide meaningful coverage of actual behavior rather than merely confirming that individual methods return expected values in isolation.

The authentication tests confirm that registration yields a valid user token, that the issued token can be used to retrieve the authenticated user profile, that guest tokens do not grant access to user-only endpoints, and that unauthenticated profile updates are rejected. These are not superficial checks. They validate that token issuance, filter-based authentication, and endpoint authorization work together correctly. Likewise, the quiz management tests confirm the full lifecycle of creating, listing, reading, updating, and deleting a quiz, while also checking guest restrictions, invalid-question rejection, and user ownership boundaries.

The room management tests are especially important because room state has more branching logic than CRUD resources do. The tests cover room creation, joining by users and guests, automatic team distribution, captain and analyst assignment, solo-room behavior, and the edge case in which a one-person team must allow the same participant to serve as both captain and analyst. These are the kinds of tests that meaningfully document domain expectations, because they show not only the happy path but also how the model behaves at the boundary of its rules.

The game engine tests exercise the most complex runtime behavior. They validate that a game can be started from a quiz, that answer selections and confirmations are stored correctly, that timer expiry advances the room through questions, that the final question produces final leaderboard and report data, that the analyst power can only be used once per game for a team, and that the host can terminate an active game explicitly. These tests are valuable because they focus on state transitions over time, which are the core technical risk in any live multiplayer workflow.

A more unit-oriented test, `OAuth2LoginServiceTest`, verifies that the Google OAuth flow preserves existing user profile fields where appropriate. This complements the broader integration tests by confirming behavior in a narrower service boundary. The combination of broad integration tests and targeted service-level verification is a reasonable testing strategy for the codebase.

From a debugging perspective, the project is relatively well structured because responsibilities are explicit and interfaces are narrow. In the backend, REST issues can be traced from controller to service to repository, while live room issues can be traced from `RoomMessageController` through `GameLoopService` and `RoomService` to `RoomRealtimeService`. On the frontend, errors can be localized to `apiClient`, Redux state transitions, or socket-event handling in `RoomSocketClient` and the application coordinator. Because room state is represented explicitly in `GameSessionResponse` and stored centrally in `roomSlice`, the developer can inspect the current authoritative session snapshot rather than inferring application state indirectly from UI behavior alone.

The current workspace was also used to verify the build and test behavior of the repository. The frontend build command `npm run build` in the `dip_quizzes` module completed successfully. During execution, Vite emitted a warning that the installed Node.js version was `18.19.1` whereas Vite prefers `20.19+` or `22.12+`. Despite that warning, the production bundle was generated successfully. This should be documented as an environment recommendation rather than as a build failure.

The backend verification command `./mvnw test` in the `dip2` module did not complete successfully in the present environment. The failure was not caused by a visible business-logic assertion failure in the tests that were examined. Instead, Mockito’s inline Byte Buddy mock maker could not initialize because the JVM environment did not provide a working agent self-attachment mechanism. In practical terms, the test suite exists, is structurally valid, and is clearly intended to run under Spring Boot test support with H2 and in-memory room storage, but successful execution may depend on a JVM configuration that permits Mockito’s agent-based behavior. This is an environmental debugging note that should appear in technical documentation because it affects reproducibility for other developers.

## 7. Build and Execution Instructions

To assemble and run the system, a developer must prepare both infrastructure services and language-specific runtime environments. The backend is contained in the `dip2` directory and is built with Maven. The frontend is contained in the `dip_quizzes` directory and is built with npm and Vite. PostgreSQL and Redis are required for the standard runtime path of the backend, although the test environment is configured separately to use H2 and an in-memory room store.

The recommended backend prerequisites are Java 17, Docker, and Docker Compose. The frontend should ideally be run with Node.js 20.19 or newer, because that matches the stated expectations of the current Vite version. While the frontend did build successfully in the observed environment with Node 18.19.1, using the recommended Node version is the more robust setup.

The infrastructure services can be started from the backend directory using Docker Compose:

```bash
cd /home/user/projects/dip/dip2
docker compose up -d postgres redis
```

The `docker-compose.yml` file defines a PostgreSQL 16 container and a Redis 7 container. PostgreSQL is exposed on port `5432` and Redis on port `6379`. The backend configuration file `src/main/resources/application.yml` expects these services by default and also supports environment-variable overrides.

The backend reads configuration values from environment variables and optionally from an imported `.env`-style properties file. At minimum, the following parameters should be defined in the runtime environment:

```env
DB_URL=jdbc:postgresql://localhost:5432/dip2
DB_USERNAME=postgres
DB_PASSWORD=postgres
JWT_SECRET=replace-this-with-a-long-32-byte-secret-key
GOOGLE_CLIENT_ID=your-google-client-id
GOOGLE_CLIENT_SECRET=your-google-client-secret
FRONTEND_OAUTH_REDIRECT=http://localhost:5173/oauth2/callback
ROOM_STORE=redis
REDIS_HOST=localhost
REDIS_PORT=6379
```

Once the environment has been prepared, the backend can be built and executed as follows:

```bash
cd /home/user/projects/dip/dip2
./mvnw clean package
./mvnw spring-boot:run
```

The application will run by default on `http://localhost:8080`. The Maven wrapper is included in the repository, which improves reproducibility by avoiding a dependency on a globally installed Maven distribution.

Backend tests can be invoked with:

```bash
./mvnw test
```

The codebase includes a dedicated test configuration in `src/test/resources/application.yml` that switches the datasource to an H2 in-memory database, disables production-style room storage by using the in-memory store, and provides test-safe JWT and OAuth values. However, as already noted in the verification section, the ability to run the full test suite may depend on JVM support for Mockito’s inline Byte Buddy mock maker in the local environment.

The frontend setup begins in the `dip_quizzes` directory. Dependencies are installed with npm:

```bash
cd /home/user/projects/dip/dip_quizzes
npm install
```

The frontend configuration is derived from environment variables using the `src/config/appConfig.ts` module. If explicit values are desired, they can be provided through a Vite environment file. A representative configuration is:

```env
VITE_API_BASE_URL=http://localhost:8080
VITE_OAUTH_BASE_URL=http://localhost:8080
VITE_WS_BASE_URL=ws://localhost:8080
```

If no explicit values are supplied, the code falls back to defaults based on `http://localhost:8080` for backend HTTP communication and a corresponding WebSocket URL for live messaging.

The frontend development server can then be started with:

```bash
npm run dev
```

Under the default Vite configuration, the application will be available at `http://localhost:5173`. To generate a production build, the following command should be used:

```bash
npm run build
```

To preview the built frontend locally:

```bash
npm run preview
```

In a standard development workflow, the complete startup sequence is therefore: first start PostgreSQL and Redis, then start the backend application, then start the frontend development server, and finally open the frontend in a browser. A typical interaction path after startup is to register or log in, create one or more quizzes, create a room, join the room from additional clients or guest sessions, distribute teams, and then begin the game. Because the system uses real-time messaging, it is useful to test room participation with multiple browser sessions or multiple devices.

## 8. Conclusion

The implemented project demonstrates a coherent and technically mature solution to a problem that goes beyond simple CRUD-based web application development. Its core strength lies in the careful separation between durable authored content and transient live-session state. By modeling quizzes and users as relational persistent entities while treating game rooms and runtime interactions as a dedicated session domain, the system avoids the architectural confusion that often arises when all data is forced through a single persistence model. The backend is layered sensibly, with thin controllers, focused services, explicit DTO contracts, and strong separation of infrastructure concerns such as security and WebSocket messaging. The frontend is equally structured, combining a typed API layer, explicit global state management, and screen-local reducers where appropriate.

The choice of Java, Spring Boot, React, TypeScript, PostgreSQL, Redis, and WebSocket/STOMP is defensible not only in general terms but specifically in relation to the implemented behavior visible in the code. Each technology addresses a real requirement of the system: relational persistence for authored content, low-latency transient state for game sessions, secure role-sensitive access, and reactive multi-user synchronization. The test suite further indicates that the system has been approached with integration behavior in mind, especially in the room-management and game-engine domains where correctness depends on time, state, and user role.

From an engineering-report perspective, the software can therefore be evaluated as a layered full-stack application whose design decisions are largely consistent with the domain complexity it addresses. The main limitations observed during repository verification were environmental rather than architectural: the backend test suite is sensitive to the JVM agent-attachment environment required by Mockito’s inline mock maker, and the frontend toolchain now prefers a newer Node.js runtime than the one currently installed in the examined workspace. These issues are important for reproducibility, but they do not undermine the essential quality of the implemented design.

Overall, the project presents a technically credible implementation of a real-time quiz platform, with clear architecture, strong separation of concerns, and a code structure that is suitable for both academic explanation and further professional development.
