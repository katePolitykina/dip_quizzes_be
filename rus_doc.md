# Отчёт о разработке и реализации программной системы

## 1. Введение

Данный документ представляет техническую документацию по этапу разработки и реализации программной системы, содержащейся в репозитории `/home/user/projects/dip`. Система не является единым исполняемым артефактом, а представляет собой согласованное full-stack приложение, состоящее из серверного модуля `dip2` и клиентского модуля `dip_quizzes`. Совместно эти модули реализуют интерактивную платформу для викторин, поддерживающую регистрацию учётных записей, гостевой доступ, создание викторин, создание игровых комнат, настройку команд, оркестрацию игры в реальном времени, оценивание на основе уверенности и формирование итоговых игровых отчётов. Таким образом, кодовая база представляет собой нечто большее, чем традиционную систему ввода и хранения данных. Она объединяет постоянные бизнес-данные, временное состояние сеанса, механизмы безопасности, временную координацию и двунаправленное сетевое взаимодействие в одном целостном техническом решении.

С точки зрения программной инженерии приложение решает два принципиально разных класса задач. Первый класс связан с долговременными данными и классическими бизнес-процессами. К нему относятся учётные записи пользователей, управление профилем, создание и обновление викторин, а также контроль доступа к авторскому контенту. Эти возможности требуют транзакционной персистентности, валидации и чётких правил владения данными. Второй класс связан с изменчивым состоянием времени выполнения. Сюда относятся состав комнаты, продвижение по вопросам в реальном времени, назначение ролей в команде, подтверждение ответов, пауза и возобновление, а также обновления таблицы лидеров, доставляемые нескольким участникам одновременно. Эти возможности требуют предсказуемого управления конкурентным доступом, низкой задержки и инфраструктуры, способной немедленно распространять изменения состояния. Реализованная архитектура отвечает этой двойственной природе задачи, разделяя постоянный контент викторин и временное состояние игровых сессий, но при этом предоставляя их как единую интегрированную платформу.

Структура репозитория ясно отражает это разделение. Серверный модуль `dip2` реализован на Java с использованием Spring Boot и предоставляет REST API, WebSocket-эндпоинты, бизнес-сервисы, персистентность, аутентификацию, авторизацию и оркестрацию состояния комнаты. Клиентский модуль `dip_quizzes` реализован на TypeScript с React и представляет собой одностраничное приложение, через которое пользователи проходят аутентификацию, управляют викторинами, входят в игровые комнаты и участвуют в живых сессиях. Вместо того чтобы рассматривать фронтенд как пассивный слой шаблонов, реализация возлагает на него существенную ответственность за маршрутизацию, управление пользовательским потоком, синхронизацию состояния и обработку событий реального времени. В то же время сервер сохраняет контроль над всеми авторитетными бизнес-решениями, что является обоснованным инженерным выбором с точки зрения согласованности и безопасности.

Данный отчёт написан непосредственно по реализованному коду, а не на основе предположительного проектного описания. Следовательно, анализ опирается на реально существующие в репозитории классы, модули, файлы конфигурации, тесты и определения сборки. Там, где реализация подразумевает неявные архитектурные решения, эти решения реконструируются и объясняются в инженерных терминах. Цель документа заключается не только в том, чтобы перечислить использованные технологии, но и в том, чтобы обосновать, почему они были выбраны, как организована архитектура программной системы, как взаимодействуют ключевые классы, каким образом были отлажены и проверены основные модули и как разработчик может собрать и запустить решение.

## 2. Обоснование технологического стека

Технологический стек, выбранный для данного проекта, соответствует масштабу, сложности и интерактивной модели реализованной системы. Серверная часть основана на Java 17 и Spring Boot 3.3.5, в то время как клиентская часть основана на TypeScript, React 19, Redux Toolkit и Vite. Кроме того, сервер использует PostgreSQL для долговременной реляционной персистентности и Redis для хранения изменчивого состояния игровых комнат. Система также применяет аутентификацию на основе JWT, вход через Google OAuth2 и обмен сообщениями по WebSocket/STOMP для обновлений в реальном времени.

Выбор **Java 17** для серверной части хорошо обоснован. Сервер отвечает за нетривиальное моделирование предметной области, контроль доступа, валидацию запросов, координацию персистентности, оркестрацию живых сессий и обработку временных событий. Во всех этих областях Java остаётся особенно сильным инструментом. Язык предлагает явную типизацию, развитую экосистему инструментов, зрелые библиотеки и предсказуемую структурную модель для систем, чья сложность обусловлена доменными правилами, а не только алгоритмической новизной. Кодовая база активно использует такие классы, как `AuthService`, `QuizService`, `RoomService`, `GameLoopService`, `JwtService`, а также структурированные DTO-records, и объектно-ориентированная модель Java естественно соответствует данному стилю реализации. Java 17 также является версией с долгосрочной поддержкой, что особенно важно для проекта, который предполагается поддерживать и развивать в течение продолжительного времени. Конфигурация дополнительно включает поддержку виртуальных потоков в Spring, что указывает на согласованность с современными моделями исполнения JVM.

Использование **Spring Boot 3.3.5** является технически оправданным, поскольку сервер должен совмещать несколько инфраструктурных аспектов в одном приложении: HTTP API, аутентификацию, OAuth2-вход, реляционную персистентность, интеграцию с Redis, валидацию и обмен сообщениями по WebSocket. Spring Boot существенно сокращает объём шаблонного кода в этих областях, не разрушая при этом архитектурную ясность. В рассматриваемом проекте REST-контроллеры остаются компактными и декларативными, а сервисы инкапсулируют бизнес-логику. Это является признаком того, что фреймворк используется корректно, а не выступает источником случайной сложности. Spring Boot также предоставляет зрелые соглашения конфигурации, средства тестирования и согласованный набор зависимостей, что особенно важно в академической и профессиональной инженерной работе, где значимы прослеживаемость и сопровождаемость.

Применение **Spring Security** не является случайным. Система различает локально зарегистрированных пользователей, пользователей, вошедших через OAuth, и гостей, а затем применяет разные уровни привилегий в зависимости от роли и конечной точки. Например, зарегистрированный пользователь может управлять викторинами и создавать комнаты, тогда как гость может присоединиться к комнате и участвовать в сессии, но не может использовать функции управления профилем или викторинами. Реализованный класс `SecurityConfig` кодирует эти ограничения напрямую и достаточно ясно. Именно для такого управления границами безопасности Spring Security и предназначен. Наличие как HTTP-аутентификации, так и WebSocket-аутентификации дополнительно усиливает обоснованность использования зрелого фреймворка безопасности вместо самодельного решения.

Выбор **Spring Data JPA** в сочетании с **PostgreSQL** оправдан природой долговременных бизнес-данных. Учётные записи пользователей, викторины, вопросы и ответы являются по своей сути реляционными сущностями. Один пользователь создаёт много викторин, одна викторина содержит много вопросов, а один вопрос содержит много ответов. JPA-сущности `User`, `Quiz`, `Question` и `Answer` отображают эту структуру напрямую. Использование JPA позволяет разработчику работать на уровне агрегатов и связей, а не вручную писать повторяющееся SQL-отображение объектов. PostgreSQL является подходящей системой управления базами данных, поскольку он транзакционен, зрел, широко распространён и надёжен для того типа структурированного контента, который хранится здесь. Код показывает, что данные авторских викторин должны быть долговечными и пригодными для запросов, что соответствует реляционной персистентности, а не документо-ориентированному или key-value хранению.

Использование **Redis** для хранения состояния комнат столь же оправдано, но уже по иным причинам. Игровые сессии являются временными и изменчивыми. Они содержат назначения участников, команды, состояние продвижения по вопросам, выборы ответов, данные таблицы лидеров, временные метки и финальные отчёты. Эта информация часто изменяется и гораздо естественнее трактуется как состояние сеанса выполнения, чем как нормализованные реляционные данные. Код формализует это через абстракцию `GameSessionStore`, для которой предусмотрены реализации как на Redis, так и в памяти. Это хорошее архитектурное решение, потому что оно отвязывает модель состояния комнаты от конкретного хранилища, одновременно признавая, что изменчивые данные живых сессий лучше обрабатывать отдельно от авторского контента. Таким образом, Redis используется не как универсальная замена базе данных, а как специализированный механизм хранения runtime-состояния.

Сервер также использует **Spring WebSocket** с **обменом сообщениями в стиле STOMP**, что необходимо для требований приложения по взаимодействию в реальном времени. Комната викторины по своей природе многопользовательская и событийно-ориентированная. Ведущий должен иметь возможность запустить игру, поставить её на паузу, продвинуть её дальше или удалить участника. Участники должны немедленно получать обновления, когда начинается вопрос, когда команда подтверждает ответ, когда изменяется гистограмма подтверждённых ответов или когда формируется итоговый отчёт. Опрос сервера через REST-эндпоинты был бы неэффективен и приводил бы к неудовлетворительному пользовательскому опыту. Поэтому WebSocket-коммуникация является правильным техническим выбором. Реализованные `RoomMessageController`, `JwtStompChannelInterceptor` и `RoomRealtimeService` вместе демонстрируют продуманную архитектуру обмена сообщениями, а не импровизированную интеграцию сокетов.

На клиентской стороне использование **TypeScript** особенно оправдано количеством контрактов данных, которыми клиент обменивается с сервером. Клиент получает полезные нагрузки аутентификации, детали викторин, снимки состояния комнат, таблицы результатов, события команд и финальные отчёты. Он также отправляет строго структурированные запросы на вход в систему, создание комнаты, обновление команд и WebSocket-команды. TypeScript полезен здесь тем, что делает эти контракты явными и проверяемыми на этапе компиляции. В клиенте реального времени непроверенные динамические объекты часто становятся серьёзным источником дефектов; текущая реализация избегает значительной части этого риска благодаря статической типизации во всех слоях пользовательского интерфейса и API.

Использование **React 19** уместно, поскольку фронтенд является состоянием-насыщенным одностраничным приложением с несколькими экранами и режимами взаимодействия: представления аутентификации, панель управления, редактор викторин, экран присоединения к комнате, лобби, экран игровой сессии и экран детализированных результатов. React особенно эффективен для управления композицией представлений, производным состоянием и условным рендерингом в такой среде. Главный компонент `App` выступает координатором состояния маршрута, начальной аутентификации, загрузки викторин, повторного входа в комнату по URL и жизненного цикла WebSocket, тогда как более мелкие компоненты сосредоточены на конкретных участках интерфейса. Такое разделение хорошо соответствует компонентной архитектуре React.

Выбор **Redux Toolkit** отражает тот факт, что не всё состояние фронтенда локально для одного компонента. Состояние аутентификации, библиотека викторин и состояние комнат являются сквозными аспектами, которые затрагивают сразу несколько представлений. Redux Toolkit предоставляет дисциплинированную структуру для асинхронных действий и мутаций глобального состояния. В данном проекте `authSlice`, `quizzesSlice` и `roomSlice` управляют логически разными областями приложения, сохраняя при этом явность переходов состояния. В то же время разработчик правильно избегает использования Redux для всего без исключения. Редактор викторин использует собственные `QuizContext` и reducer, поскольку состояние редактирования локально для этого сценария и выигрывает от более лёгкой, экранно-локальной модели. Такая смешанная стратегия является примером уместного, а не избыточного управления состоянием.

Выбор **Vite** в качестве инструмента сборки фронтенда также уместен. Vite обеспечивает быстрый запуск среды разработки, простую интеграцию с TypeScript и современное поведение сборщика для React-приложений. `package.json` и сценарии сборки в репозитории демонстрируют минималистичный, но эффективный pipeline разработки, построенный вокруг `vite`, `tsc -b` и ESLint. Это практичный выбор для фронтенда, которому полезна быстрая итерация, но не требуется тяжёлая framework-specific система сборки.

Хотя репозиторий не предписывает конкретную среду разработки, наиболее подходящей **IDE** для этого решения является IntelliJ IDEA с поддержкой Java, Spring, Maven, TypeScript и React. Проект охватывает конфигурирование backend-фреймворка, JPA-сущности, выполнение тестов, инфраструктуру на основе Docker и разработку фронтенд-SPA. Единая среда, способная переходить от контроллера к сервису и репозиторию, а также от TypeScript-компонента к reducer и API-клиенту, заметно повышает производительность инженерной работы и уменьшает затраты на переключение контекста. По этой причине IntelliJ IDEA является наиболее обоснованным выбором IDE для реализованного технологического стека.

## 3. Архитектура программной системы и интерфейсы

Архитектуру системы наиболее точно можно описать как **многоуровневую full-stack клиент-серверную систему**. Это не микросервисная архитектура, поскольку backend развёртывается как одно приложение и инкапсулирует внутри себя несколько обязанностей. Одновременно это не монолитный интерфейс, обслуживаемый серверными шаблонами. Фронтенд представляет собой автономное одностраничное приложение, взаимодействующее с сервером через HTTP и WebSocket-интерфейсы. В результате формируется модульная архитектура, в которой backend и frontend разделены чётко определёнными контрактами, оставаясь при этом тесно согласованными вокруг одной предметной области.

### 3.1 Архитектура серверной части

Внутри backend основным архитектурным шаблоном является **многоуровневая сервисно-ориентированная структура**. Внешним слоем выступает слой представления, представленный REST-контроллерами и WebSocket message controller. Эти классы намеренно сделаны тонкими. `AuthController`, `UserController`, `QuizController` и `RoomController` принимают валидированные запросы и сразу делегируют их сервисным классам. `RoomMessageController` играет аналогичную роль для входящих STOMP-сообщений. Это положительное свойство архитектуры, поскольку оно предотвращает случайное проникновение бизнес-правил в транспортно-зависимый код и делает HTTP- и WebSocket-эндпоинты понятными.

Основная бизнес-логика сосредоточена в **сервисном слое**. `AuthService` обрабатывает регистрацию пользователей, проверку учётных данных и выдачу гостевых токенов. `UserService` отвечает за получение данных пользователя и обновление профиля. `QuizService` проверяет владение викториной, валидирует структуру вопросов, отображает DTO в сущности и формирует ответные DTO. `RoomService` управляет созданием комнаты, членством, распределением по командам, назначением ролей и действиями модерации на уровне комнаты. `GameLoopService` выполняет наиболее сложную оркестрацию, включая запуск игр, инициализацию runtime-вопросов на основе сохранённого контента викторины, отслеживание ответов, планирование завершения вопросов, вычисление очков, пересчёт таблицы лидеров и генерацию итоговых отчётов. `RoomRealtimeService` имеет более узкую ответственность: он служит фасадом трансляции поверх слоя обмена сообщениями, чтобы другие сервисы не зависели от деталей формирования топиков. Такое распределение обязанностей является согласованным и удерживает каждый класс в рамках одной доменной роли.

Ниже сервисного слоя проект использует не одну, а две стратегии доступа к данным. Долговременный авторский контент хранится через **слой персистентности**, построенный на Spring Data JPA-репозиториях. `UserRepository` и `QuizRepository` используются бизнес-сервисами, работающими с постоянными сущностями. В противоположность этому, изменчивое состояние комнаты управляется через абстракцию `GameSessionStore`, которая может иметь реализацию на Redis или в памяти. Это особенно важное архитектурное решение. Если бы состояние комнаты было принудительно сведено к той же модели персистентности, что и викторины с пользователями, дизайн оказался бы более громоздким и менее отзывчивым. Разделяя постоянные данные авторства и временные данные игрового процесса, система отражает реальный жизненный цикл информации, с которой работает.

Backend также включает отдельный **слой безопасности и инфраструктуры**. `SecurityConfig` определяет правила авторизации конечных точек, интегрирует JWT-фильтрацию и конфигурирует OAuth2-login. `JwtAuthenticationFilter` аутентифицирует HTTP-запросы через bearer-токены. `JwtService` создаёт и разбирает токены как для обычных пользователей, так и для гостей. `WebSocketConfig` включает STOMP-обмен сообщениями и конфигурирует эндпоинт `/ws`. `JwtStompChannelInterceptor` аутентифицирует входящие WebSocket-соединения и подписки, а `WebSocketSessionRegistry` поддерживает отслеживание сессий и принудительное отключение. Эти классы инфраструктурны, а не предметно-ориентированы, но критически важны, потому что корректность приложения зависит не только от бизнес-логики, но и от того, кому разрешено выполнять какие действия.

С точки зрения внутреннего взаимодействия backend доминирующим шаблоном является цепочка **controller -> service -> repository/store**, где DTO находятся на границе, а доменные/runtime-объекты - в середине. Например, запрос на создание викторины проходит от `QuizController.createQuiz(...)` к `QuizService.createQuiz(...)`, где валидируется, отображается в агрегат `Quiz` и сохраняется через `QuizRepository`. Запрос на запуск комнаты проходит от `RoomMessageController.startGame(...)` к `GameLoopService.startGame(...)`, который получает соответствующую викторину через `QuizRepository`, преобразует сохранённые сущности `Question` и `Answer` в runtime-объекты `QuestionState` и `QuestionAnswerState`, сохраняет обновлённый `GameSession` через `RoomService` и `GameSessionStore`, а затем рассылает новое состояние через `RoomRealtimeService`. Этот путь взаимодействия прямой, структурированный и соответствует многоуровневой архитектуре.

### 3.2 Интерфейсы серверной части

Backend предоставляет две основные категории интерфейсов: **синхронные REST-интерфейсы** и **асинхронные WebSocket/STOMP-интерфейсы**. REST-эндпоинты используются там, где естественна и достаточна модель request-response. Сюда относятся аутентификация, получение и изменение профиля, CRUD-операции над викторинами, создание комнаты, операции входа и выхода из комнаты, а также управление распределением команд. Эти интерфейсы представлены методами контроллеров `AuthController`, `UserController`, `QuizController` и `RoomController`.

WebSocket/STOMP-интерфейс используется там, где необходимы низкая задержка и обновления, инициируемые сервером. Входящие команды маршрутизируются через application destinations, такие как `/app/rooms/{pin}/moderation`, `/app/rooms/{pin}/game/start`, `/app/rooms/{pin}/teams/{teamId}/selection`, `/app/rooms/{pin}/teams/{teamId}/confirm` и `/app/rooms/{pin}/teams/{teamId}/sort-answers`. Исходящее распространение состояния отправляется в topic destinations, такие как `/topic/rooms/{pin}`, `/topic/rooms/{pin}/leaderboard` и `/topic/rooms/{pin}/teams/{teamId}`. Это различие между каналами команд и каналами событий является важной частью дизайна, поскольку оно обеспечивает сохранение за backend роли единственного авторитетного владельца состояния комнаты, в то время как клиенты остаются потребителями и инициаторами, но не прямыми модификаторами общего состояния.

### 3.3 Архитектура клиентской части

Фронтенд следует параллельной, но клиентски-специфичной структуре. На верхнем уровне находится **слой представления**, состоящий из React-компонентов, представляющих экраны приложения и переиспользуемые элементы интерфейса. Компонент `App` координирует глобальный поток приложения, тогда как такие компоненты, как `Dashboard`, `QuizEditorLayout`, `JoinView`, `ActiveLobby`, `GameSessionScreen` и `DetailedResultScreen`, отображают конкретные состояния пользовательского сценария. Это создаёт такую структуру представления, в которой логика экранов остаётся видимой и относительно простой для понимания.

Ниже слоя представления располагается **слой управления состоянием**, который объединяет срезы Redux Toolkit с локальным reducer на основе context для редактора викторин. Такое разделение является технически уместным. Состояние аутентификации, состояние комнаты и каталог викторин являются глобальными аспектами и поэтому обрабатываются `authSlice`, `quizzesSlice` и `roomSlice`. Редактор викторин, напротив, моделируется через `QuizContext`, поскольку его состояние богато, интерактивно и в значительной степени ограничено одним рабочим сценарием. Это позволяет избежать как избыточного проброса пропсов, так и ненужной глобализации локального состояния представления.

Frontend также содержит **коммуникационный слой**. HTTP-коммуникация инкапсулирована в `apiClient`, который централизует формирование запросов, управление токенами и обработку ошибок. Обмен в реальном времени инкапсулирован в `RoomSocketClient`, который управляет WebSocket-подключением, STOMP-кадрами, подписками, переподключением и передачей событий на уровень приложения. Такое разделение гарантирует, что компоненты пользовательского интерфейса не взаимодействуют напрямую с низкоуровневыми деталями транспорта.

## 5. Детали реализации

Реализация системы примечательна тем, насколько последовательно в ней разделяются обязанности при сохранении общей понятности потока управления. Хорошим примером является процесс аутентификации. `AuthController` лишь предоставляет эндпоинты `/api/auth/register`, `/api/auth/login` и `/api/auth/guest`. Реальная логика находится в `AuthService`, который нормализует пользовательский ввод, проверяет наличие дублирующихся адресов электронной почты, использует настроенный password encoder для хеширования паролей, сохраняет новых пользователей и выдаёт JWT-токены через `JwtService`. Путь гостевой аутентификации следует тому же общему шаблону, но обходит создание постоянной пользовательской записи и вместо этого генерирует временную идентичность, встроенную в полезную нагрузку токена. Это прагматичное решение, поскольку оно позволяет гостям использовать ту же инфраструктуру авторизации и WebSocket, что и зарегистрированным пользователям, не вводя вторую модель идентичности во всей остальной системе.

Процесс создания викторин столь же дисциплинирован. `QuizService` не просто сохраняет входящие JSON-данные. Перед сохранением викторины он проверяет, что каждый вопрос содержит от двух до четырёх вариантов ответа и что хотя бы один ответ отмечен как правильный. Это важный пример валидации бизнес-правил на стороне сервера: даже если фронтенд пытался бы обеспечить то же самое правило, backend остаётся авторитетным источником истины. После валидации входящий запрос отображается в иерархию сущностей `Quiz -> Question -> Answer`. Методы `replaceQuestions(...)` и `replaceAnswers(...)` особенно важны, поскольку они трактуют объекты викторины и вопроса как агрегаты, владеющие своими дочерними коллекциями. Это упрощает семантику обновления и помогает избежать фрагментированной логики мутации коллекций.

Подсистемы комнаты и игры содержат наиболее сложную реализационную логику в репозитории. `RoomService` создаёт игровые сессии, выделяет уникальные PIN-коды из ограниченного алфавита, обеспечивает ограничения на уровне лобби, предотвращает дублирование никнеймов в комнате, управляет входом и выходом участников, распределяет игроков по командам и назначает или обновляет роли. Эти операции обёрнуты в механизм `executeLocked(...)`, предоставляемый абстракцией хранилища сессий. Это важная инженерная особенность. В среде реального времени конкурентный доступ к состоянию сессии неизбежен. Без явной блокировки или атомарного контроля обновлений такие операции, как несколько одновременных входов, обновление ролей или отправка ответов, могли бы повредить состояние комнаты. Реализация решает эту проблему, централизуя все изменяемые операции комнаты за lock-aware API хранилища.

После начала игры управление переходит к `GameLoopService`. Когда ведущий запускает игру, сервис проверяет, что выбранная викторина принадлежит инициирующему пользователю, загружает сохранённую викторину, преобразует каждый сохранённый вопрос в runtime-объект `QuestionState`, проверяет структурную готовность комнаты к игре, применяет overrides для confidence-based marking, если они предоставлены, сбрасывает прогресс игры и запускает первый вопрос. С этого момента класс становится координатором автомата состояний. Он принимает выборы ответов команд, обеспечивает правило, что подтверждать ответы может только капитан, при необходимости применяет уровни уверенности, записывает данные ответов отдельных игроков, отслеживает временные метки для анализа времени отклика, рассылает события выбора и гистограммы, планирует завершение вопросов с помощью `ScheduledExecutorService`, вычисляет очки по завершении вопроса и либо переводит игру к следующему вопросу, либо завершает её, формируя таблицу лидеров и итоговый отчёт. Логика носит state-driven и time-aware характер, что и требуется от подобной подсистемы.

Механизм вычисления очков сам по себе компактен, но концептуально последователен. `ScoringUtility` получает базовый вес, флаг корректности, speed factor, уровень уверенности и применимые настройки confidence-based marking. Затем он вычисляет множитель очков в зависимости от того, был ли ответ правильным и насколько уверенно команда его заявила. Правильные ответы могут получать большее вознаграждение при высокой уверенности, тогда как неправильные ответы могут влечь более сильный штраф, если уровень уверенности оказался необоснованным. Дополнительная корректировка по скорости применяется к правильным ответам. Этот дизайн аккуратно отделяет математическую модель подсчёта от оркестрационного кода, который подготавливает входные параметры.

Путь трансляции событий реального времени также реализован качественно. Бизнес-сервисы не формируют STOMP-топики вручную в каждой точке кода. Вместо этого `RoomRealtimeService` предоставляет методы вроде `broadcastRoomState(...)`, `broadcastRoomEvent(...)`, `broadcastTeamSelection(...)`, `broadcastLeaderboard(...)` и `broadcastTeamEvent(...)`. Это изолирует детали message broker от доменной логики и делает сервисы более читаемыми. На клиентской стороне комплементарную роль выполняет `RoomSocketClient`. Он открывает WebSocket-соединение, отправляет STOMP-кадр `CONNECT` с bearer-токеном, подписывается на топики комнаты и команд, разбирает входящие кадры, переподключается с экспоненциальной задержкой после обрыва и передаёт полезные нагрузки сообщений на уровень приложения.

Главный компонент фронтенда `App` демонстрирует прагматичную стратегию интеграции. Вместо зависимости от крупного роутингового фреймворка он поддерживает состояние маршрута с помощью browser history API и явных функций разбора пути. Затем он координирует начальную аутентификацию, получение профиля, загрузку викторин, повторный вход в комнату по URL и жизненный цикл сокета в зависимости от текущего экрана и аутентифицированного состояния. Это не единственный возможный подход, но он внутренне согласован и избегает лишней framework complexity. Redux-slice далее управляют общесистемными доменами данных. `authSlice` сохраняет состояние сессии и профиля, `quizzesSlice` управляет библиотекой викторин и активной викториной, а `roomSlice` хранит снимок живой сессии, статус соединения, данные гистограммы, скрытые ответы, обновления таблицы лидеров и состояние удаления из комнаты. Редактор викторин, напротив, использует `QuizContext` и reducer, поскольку этот паттерн взаимодействия более локален и выигрывает от reducer-семантики без необходимости глобального экспонирования через Redux.

## 6. Тестирование, отладка и проверка интеграции

Набор тестов в backend-модуле показывает, что проект проверялся преимущественно с помощью интеграционных тестов. Это оправданный выбор. Наиболее значимые риски в данном приложении связаны не с изолированной арифметикой или тривиальными вспомогательными функциями, а с взаимодействием между валидацией, персистентностью, безопасностью, состоянием комнаты и временными переходами. По этой причине такие тесты, как `AuthFlowIntegrationTest`, `QuizManagementIntegrationTest`, `RoomManagementIntegrationTest` и `GameEngineIntegrationTest`, дают содержательное покрытие реального поведения, а не просто подтверждают, что отдельные методы возвращают ожидаемые значения в изоляции.

Тесты аутентификации подтверждают, что регистрация выдаёт корректный пользовательский токен, что выданный токен может быть использован для получения профиля аутентифицированного пользователя, что гостевые токены не дают доступа к пользовательским эндпоинтам и что обновление профиля без аутентификации отклоняется. Это не поверхностные проверки. Они демонстрируют, что выдача токенов, фильтрация аутентификации и авторизация эндпоинтов корректно работают совместно. Аналогично тесты управления викторинами подтверждают полный жизненный цикл создания, получения списка, чтения, обновления и удаления викторины, а также проверяют ограничения для гостей, отклонение некорректных вопросов и границы владения контентом пользователем.

Тесты управления комнатами особенно важны, поскольку состояние комнаты имеет больше ветвящейся логики, чем CRUD-ресурсы. Тесты охватывают создание комнаты, вход зарегистрированных пользователей и гостей, автоматическое распределение по командам, назначение капитана и аналитика, поведение в одиночной комнате и пограничный случай, при котором в команде из одного человека один и тот же участник должен иметь возможность быть одновременно капитаном и аналитиком. Это те тесты, которые действительно документируют доменные ожидания, поскольку показывают не только happy path, но и поведение модели на границах её правил.

Тесты игрового движка проверяют наиболее сложное runtime-поведение. Они подтверждают, что игру можно запустить на основе викторины, что выборы и подтверждения ответов сохраняются корректно, что истечение таймера продвигает комнату по вопросам, что финальный вопрос формирует итоговые данные таблицы лидеров и отчёта, что способность аналитика может быть использована только один раз за игру для команды и что ведущий может явно завершить активную игру. Эти тесты ценны тем, что сосредоточены на переходах состояния во времени, а именно это и является основным техническим риском в любой live multiplayer workflow.

Более узкий unit-oriented тест `OAuth2LoginServiceTest` проверяет, что поток Google OAuth сохраняет существующие поля пользовательского профиля там, где это необходимо. Это дополняет более широкие интеграционные тесты, подтверждая корректность поведения в рамках меньшей сервисной границы. Сочетание широких интеграционных тестов и целевых сервисных проверок представляет собой разумную стратегию тестирования для данной кодовой базы.

С точки зрения отладки проект структурирован достаточно хорошо, поскольку обязанности явны, а интерфейсы узки. В backend проблемы REST можно прослеживать от контроллера к сервису и репозиторию, тогда как проблемы live room можно прослеживать от `RoomMessageController` через `GameLoopService` и `RoomService` к `RoomRealtimeService`. Во frontend ошибки можно локализовать в `apiClient`, переходах состояния Redux или обработке socket-событий в `RoomSocketClient` и координаторе приложения. Поскольку состояние комнаты явно представлено в `GameSessionResponse` и централизованно хранится в `roomSlice`, разработчик может инспектировать текущий авторитетный снимок сессии, а не выводить состояние приложения косвенно из поведения интерфейса.

Текущее рабочее окружение также использовалось для проверки поведения сборки и тестов репозитория. Команда сборки фронтенда `npm run build` в модуле `dip_quizzes` выполнилась успешно. Во время выполнения Vite выдал предупреждение о том, что установленная версия Node.js равна `18.19.1`, тогда как Vite предпочитает `20.19+` или `22.12+`. Несмотря на это предупреждение, production bundle был сформирован успешно. Это следует документировать как рекомендацию по окружению, а не как ошибку сборки.

Команда проверки backend `./mvnw test` в модуле `dip2` не завершилась успешно в текущем окружении. Ошибка не была вызвана видимым падением бизнес-логических проверок в рассмотренных тестах. Вместо этого inline Byte Buddy mock maker библиотеки Mockito не смог инициализироваться, поскольку JVM-окружение не предоставило рабочего механизма self-attachment агента. Практически это означает, что тестовый набор существует, структурно корректен и явно предназначен для выполнения под Spring Boot test support с H2 и in-memory room storage, однако успешный запуск может зависеть от конфигурации JVM, допускающей agent-based поведение Mockito. Это важное замечание по воспроизводимости, которое должно присутствовать в технической документации.

Логика автоматического распределения и назначения ролей присутствует в `RoomService`, а изученные тесты управления комнатой покрывают назначение капитана и аналитика, включая пограничные случаи. |
| 18 | Идёт живая командная игра, и роли Captain и Analyst уже назначены. | Попытаться подтвердить финальный командный ответ с учётной записью Analyst. | Действие блокируется, поскольку только Captain может подтверждать окончательный ответ. | Реализовано и подтверждено тестами. `GameLoopService.confirmTeamAnswer(...)` явно отклоняет попытки подтверждения от пользователей, не являющихся капитаном. |
| 19 | Идёт живая командная игра, назначен Analyst, и специальная способность ещё не использовалась. | Активировать способность аналитика по удалению ответов один раз, затем попытаться использовать её повторно. | Система скрывает половину неправильных ответов и разрешает использовать способность только один раз за игру. | Реализовано и подтверждено тестами. `GameLoopService.useSortAnswers(...)` скрывает неправильные ответы и предотвращает повторное использование, а `GameEngineIntegrationTest` проверяет поведение однократного использования. |
| 20 | Вопрос активен, ответы подтверждаются, а панель ведущего открыта. | Наблюдать гистограмму ответов до закрытия раунда, пока участники отправляют и подтверждают ответы. | Панель обновляется в реальном времени, отображая распределение ответов по вариантам. | Реализовано в коде и частично подтверждено тестами. Backend генерирует события `ANSWER_HISTOGRAM`, а frontend сохраняет состояние гистограммы, хотя полная проверка UI-рендеринга в реальном времени в изученных тестах подтверждена не была. |

## 7. Инструкции по сборке и запуску

Чтобы собрать и запустить систему, разработчику необходимо подготовить как инфраструктурные сервисы, так и языковые среды выполнения. Backend расположен в каталоге `dip2` и собирается с помощью Maven. Frontend расположен в каталоге `dip_quizzes` и собирается через npm и Vite. PostgreSQL и Redis необходимы для стандартного сценария запуска backend, хотя тестовое окружение отдельно настроено на использование H2 и in-memory room store.

Рекомендуемые требования для backend - Java 17, Docker и Docker Compose. Для frontend желательно использовать Node.js 20.19 или новее, поскольку именно эта версия соответствует ожиданиям текущей версии Vite. Хотя frontend успешно собрался в наблюдаемом окружении с Node 18.19.1, использование рекомендуемой версии Node является более надёжной конфигурацией.

Инфраструктурные сервисы можно запустить из каталога backend с помощью Docker Compose:

```bash
cd /home/user/projects/dip/dip2
docker compose up -d postgres redis
```

Файл `docker-compose.yml` определяет контейнер PostgreSQL 16 и контейнер Redis 7. PostgreSQL публикуется на порту `5432`, а Redis - на порту `6379`. Файл конфигурации backend `src/main/resources/application.yml` по умолчанию ожидает доступности именно этих сервисов и также поддерживает переопределение через переменные окружения.

Backend читает значения конфигурации из переменных окружения и, при необходимости, из подключаемого файла свойств в стиле `.env`. Минимально в окружении должны быть определены следующие параметры:

```env
DB_URL=jdbc:postgresql://localhost:5432/dip2
DB_USERNAME=postgres
DB_PASSWORD=postgres
JWT_SECRET=replace-this-with-a-long-32-byte-secret-key
GOOGLE_CLIENT_ID=your-google-client-id
GOOGLE_CLIENT_SECRET=your-google-client-secret
FRONTEND_OAUTH_REDIRECT=http://localhost:5173/oauth2/callback
ROOM_STORE=redis
REDIS_HOST=localhost
REDIS_PORT=6379
```

После подготовки окружения backend можно собрать и запустить следующим образом:

```bash
cd /home/user/projects/dip/dip2
./mvnw clean package
./mvnw spring-boot:run
```

Приложение по умолчанию будет доступно по адресу `http://localhost:8080`. Maven Wrapper включён в репозиторий, что повышает воспроизводимость, поскольку устраняет зависимость от глобально установленного дистрибутива Maven.

Тесты backend можно запускать командой:

```bash
./mvnw test
```

Кодовая база включает отдельную тестовую конфигурацию в `src/test/resources/application.yml`, которая переключает datasource на H2 in-memory database, отключает production-style room storage, используя in-memory store, и предоставляет безопасные для тестов JWT- и OAuth-значения. Однако, как уже отмечалось в разделе проверки, возможность запустить полный набор тестов может зависеть от поддержки JVM для inline Byte Buddy mock maker, используемого Mockito.

Настройка frontend начинается в каталоге `dip_quizzes`. Зависимости устанавливаются через npm:

```bash
cd /home/user/projects/dip/dip_quizzes
npm install
```

Конфигурация frontend выводится из переменных окружения с помощью модуля `src/config/appConfig.ts`. Если требуется задать явные значения, их можно передать через Vite environment file. Пример конфигурации:

```env
VITE_API_BASE_URL=http://localhost:8080
VITE_OAUTH_BASE_URL=http://localhost:8080
VITE_WS_BASE_URL=ws://localhost:8080
```

Если явные значения не заданы, код использует значения по умолчанию, основанные на `http://localhost:8080` для HTTP-коммуникации с backend и соответствующем WebSocket URL для живого обмена сообщениями.

Сервер разработки frontend затем можно запустить так:

```bash
npm run dev
```

В стандартной конфигурации Vite приложение будет доступно по адресу `http://localhost:5173`. Чтобы сформировать production-сборку, следует использовать команду:

```bash
npm run build
```

Чтобы локально просмотреть собранный frontend:

```bash
npm run preview
```

В стандартном процессе разработки полная последовательность запуска такова: сначала запускаются PostgreSQL и Redis, затем backend-приложение, затем сервер разработки frontend, и после этого frontend открывается в браузере. Типичный путь взаимодействия после старта состоит в регистрации или входе, создании одной или нескольких викторин, создании комнаты, подключении к комнате из дополнительных клиентских сессий или гостевых сессий, распределении команд и запуске игры. Поскольку система использует обмен сообщениями в реальном времени, полезно проверять участие в комнате с нескольких браузерных сессий или нескольких устройств.

## 8. Заключение

Реализованный проект демонстрирует согласованное и технически зрелое решение задачи, выходящей за рамки простой CRUD-ориентированной веб-разработки. Его основная сила заключается в аккуратном разделении между долговечным авторским контентом и временным состоянием живой сессии. Моделируя викторины и пользователей как постоянные реляционные сущности и рассматривая игровые комнаты и runtime-взаимодействия как отдельную доменную область сессий, система избегает архитектурной путаницы, которая часто возникает, когда все данные принудительно проводят через одну модель персистентности. Backend разумно многослоен: тонкие контроллеры, сфокусированные сервисы, явные DTO-контракты и сильное разделение инфраструктурных аспектов вроде безопасности и WebSocket-коммуникации. Frontend столь же структурирован, сочетая типизированный API-слой, явное глобальное управление состоянием и локальные reducer-ы там, где это уместно.

Выбор Java, Spring Boot, React, TypeScript, PostgreSQL, Redis и WebSocket/STOMP оправдан не только в общих терминах, но и конкретно по отношению к реализованному поведению, видимому в коде. Каждая технология отвечает реальному требованию системы: реляционная персистентность для авторского контента, низкозадержочное временное состояние для игровых сессий, защищённый role-sensitive доступ и реактивная многопользовательская синхронизация. Набор тестов дополнительно показывает, что разработка системы велась с учётом интеграционного поведения, особенно в областях room management и game engine, где корректность зависит от времени, состояния и роли пользователя.

С точки зрения инженерного отчёта программное обеспечение может быть оценено как многоуровневое full-stack приложение, чьи проектные решения в целом соответствуют сложности решаемой предметной области. Основные ограничения, выявленные при проверке репозитория, носят скорее характер особенностей окружения, чем архитектурных проблем: backend-набор тестов чувствителен к JVM-окружению, необходимому для agent-attachment в Mockito inline mock maker, а toolchain frontend теперь предпочитает более новую версию Node.js, чем установленная в исследованном рабочем пространстве. Эти моменты важны для воспроизводимости, но не подрывают базовое качество реализованного дизайна.

В целом проект представляет собой технически убедительную реализацию платформы викторин в реальном времени с ясной архитектурой, сильным разделением обязанностей и структурой кода, подходящей как для академического описания, так и для дальнейшего профессионального развития.
